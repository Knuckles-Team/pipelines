# CI standard (shared pieces)

Pipelines owns the reusable parts of the fleet CI standard; each repository calls them at `@main`. The checks they run are the [gate standard](gate-standard.md).

- `gates_pipeline.yml`: one `gates` job. Pull requests run the caller's pre-commit file at the commit stage and the pre-push stage over `--from-ref/--to-ref`; a main push sets `all-files: true`. Then the affected-test subset from `pr-test-scope`. Inputs: `config`, `ci-config`, `test-scope`, `src-root`, `runner`, `rust`, `all-files`, `extra-manual-hooks`, `skip-hooks`, `setup-command`, `uv-cache-local-path`, `docs-only-paths`, `timeout-minutes`. The optional `uv-cache-local-path` selects the setup action cache directory; an empty value preserves its default. Every input has a default. On `push` events the workflow adds `spec-trailers` to `SKIP`: trailers are a property of pull request commits and a squash merge does not carry them; pull request runs always enforce the hook.
- `gates_pipeline.yml` skips the pre-push `tests-fast` hook (and the deprecated `fast-tests` id) when `test-scope` is set, because its affected-test step runs the same subset without the local cap.
- `connector_pr_pipeline.yml` (PIPE-RELEASE-R011): the connector pull request workflow. It wraps `gates_pipeline.yml` with `config: .pre-commit-config.yaml`, `stages: pre-commit` and a 10-minute cap, then runs the affected unit tests. It never publishes. Input `sync-args` (default `--all-extras --all-groups`) sets the `uv sync --frozen` arguments for a connector whose extras cannot all build on a CPU runner. A connector adds a caller on `pull_request`.
- `container_pipeline.yml` runs the published-wheel preflight (PIPE-RELEASE-R012.1) on each main-branch connector target before the builder, registry login or image build. It derives a sole connector distribution/module and the target package extra from reviewed HEAD, including a bare exact pin when MCP is supplied by a base dependency, includes the deterministic ontology files generated into release wheels, and refuses ambiguous identities, unavailable public evidence or untracked selected custom Dockerfiles. It then ends with a verification step (PIPE-RELEASE-R012). A connector release publishes the PyPI version and the `<version>-mcp` image, and the run fails when either is missing. The `release-standard` hook (PIPE-RELEASE-R013) warns when a connector lacks a tracked `docker/Dockerfile` or a central container job that can render the canonical file, or lacks an enabled `container_pipeline.yml` job; a selected custom Dockerfile remains tracked and caller-owned.
- Release speed (PIPE-RELEASE-R014 to R016). `container_pipeline.yml` reuses one named BuildKit builder (`ci-shared`) per runner pod instead of creating and removing one per job, replaces it when it will not boot, and prunes its local cache to 30 GB; the per-target registry `buildcache-*` tags stay. Wheel readiness proves the runtime profiles concurrently (at most four, declared order kept) and installs with `--no-compile`; the public-index, wheel-only and no-cache rules are unchanged. `publish-python-package` keeps uv downloads and managed interpreters in the runner tool cache.
- `main_pipeline.yml`: the main and release-tag workflow. Job `tests` runs the full suite; job `supply-chain` runs one dependency audit (`pip-audit` over the runtime lock, or `cargo deny check advisories` with `rust: true`). Inputs: `test-scope`, `runner`, `rust`, `rust-manifest-path` (Cargo.toml directory layout other than the root), `backward-module` (`none` skips the import for a native-only wheel), `setup-command`, `timeout-minutes`. It never publishes; release workflows stay with each repository.
- `advisory_pipeline.yml`: the weekly advisory workflow. It runs the advisory `pipelines-hook` gates, codespell, vulture, bandit and any `extra-commands`, writes one Markdown report to the job summary and the `advisory-report` artifact, and never fails. Inputs: `gates`, `python-tools`, `extra-commands`, `scanners`, `runner`.
- Concurrency belongs to the caller: PR group `pr-<workflow>-<number>` and main group `main-<workflow>` cancel superseded runs; release and pages groups never cancel. The workflow header carries the copyable block.
- Input `docs-only-paths` (default empty): space-separated bash patterns of docs and spec paths. When every file in a pull request diff matches one, the job passes right after checkout. A caller that sets it drops `paths-ignore` from `pull_request` and has no skip companion, so exactly one `gates / gates` check exists. A skip run under the same name can then never mask a failing real run on a mixed code and docs pull request.
- `templates/workflows/gates-skip.yml` and every `*-skip.yml` companion are retired: `docs-only-paths` replaces them, and a repository deletes its companion when it adopts the templates below. `gates-skip.yml` stays only as a template for a repository that has not migrated.
- `python_pipeline.yml` input `require-tag` (default `false`): when `true` the job fails before building unless the ref is a `v*` tag. A release workflow triggered by `push: tags: ['v*']` sets it.
- Hook `fast-tests` (pre-push): affected tests only, 120 s cap, base from `PRE_COMMIT_FROM_REF`.
- Local hooks follow the [pre-commit standard](precommit-standard.md): only fast checks at pre-commit and pre-push. The CI-only gates are in `.config/ci-gates.yaml`, and the `ci-config` input of `gates_pipeline.yml` runs them.

## Required status check

The one required status check is the caller aggregate job `CI required` (job `ci-required`, `name: CI required`). It lives in the caller, because a check produced inside a reusable workflow is named `<caller> / <job>`. It runs `if: always()`, needs every PR job, fails when any needed job ended `failure` or `cancelled`, and passes when jobs were skipped (docs-only or path scope). A repository's ruleset requires only `CI required`; `gates / gates` is the older name and is replaced once a repository's first green `CI required` exists.

- `templates/workflows/ci.yml` is the standard caller: `pull_request` (main), `push` (main), nightly `schedule` and `workflow_dispatch`; caller-side concurrency as above; job `gates` (`gates_pipeline.yml` with `docs-only-paths`), job `full` (`main_pipeline.yml` with `backward-python: "3.12"`, never on pull requests), a commented slot for repository-specific fast jobs behind path filters, and `ci-required`. Pull requests run Python 3.14 only; 3.12 runs on main and nightly through `backward-python`.
- `release.yml` never runs on `pull_request`: tags (`v*`) and `workflow_dispatch` only. Anything a PR needs belongs in `ci.yml`.
- Prose lint (`ste-staged`, `ste-advisory`) is advisory everywhere and never part of `CI required`.
- `.github/workflows/auto_merge_pipeline.yml` is the reusable auto-merge gate (input `required-check`, default `CI required`; optional secret `merge-token`). It fetches `scripts/auto_merge.py` from pipelines at `main` and never checks out the pull request. The script arms `gh pr merge --auto --match-head-commit` only when the base branch requires the check and that check run concluded `success` on the exact head SHA; any other check name, a missing required check, a draft or a non-main base is a no-op. The caller is `templates/workflows/auto_merge.yml`: it triggers on `check_run` only (no `pull_request_target`, supply-chain SC-GHA-005), declares `permissions: {}` at the top and grants write to the one job (SC-GHA-004).
- `scripts/apply_repo_ci_settings.sh [--dry-run] <owner/repo>` sets `allow_auto_merge`, `delete_branch_on_merge` and the "Main integrity" ruleset (deletion, non-fast-forward, required check `CI required` only). It is idempotent and refuses, changing nothing, until the default branch has a completed successful `CI required` check run. The orchestrator runs it per repository after that first green run, never before.

## Agent contract

Every repository gives a cold agent the same setup and the same orientation (PIPE-CONNSPEC-R175 to R177):

- `scripts/bootstrap.sh` is idempotent and non-interactive. It installs a current uv (via `pip install --user`, never a piped network installer: SC-INSTALL-001), the Python pinned in `.python-version` (default 3.14), runs `uv sync --locked` (plain `uv sync` until the repository has a `uv.lock`), installs the pre-commit and pre-push hooks, and prints the gate command. A repository with extra setup (sibling pins, native builds) extends the script and keeps these steps.
- `AGENTS.md` carries the block between `<!-- agent-contract:start -->` and `<!-- agent-contract:end -->`. The block states the **Owner boundary** (with a link to [ecosystem boundaries](ecosystem-boundaries.md)), **Setup** (`scripts/bootstrap.sh`), **Gates** (`uvx pre-commit run --all-files`), **Commits** (Spec trailer, assisting-agent `Co-Authored-By:` trailer, explicit staging, own Git identity) and a link to the [organization AGENTS.md](https://github.com/Knuckles-Team/.github/blob/main/AGENTS.md). The text is tool-neutral. Content outside the markers belongs to the repository. `CLAUDE.md`, where present, only imports `@AGENTS.md`.
- The pre-push hook `agent-contract` flags a missing `scripts/bootstrap.sh` or one that trips SC-INSTALL-001/002, a missing `AGENTS.md`, or a missing or incomplete block. It warns (exit 0) until the fleet has converged; `--strict` blocks.
