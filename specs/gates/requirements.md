| `PIPE-GATES-R001` | **Pre-land fast set and post-land full set.** The eight blocking gates partition into a pre-land fast set and a post-land full set. The fast set is `format`, `hygiene`, `secrets`, `types`, and `tests-fast`; it runs server-side against the changeset's tree in seconds and decides whether the changeset lands. The full set is the remaining blocking gates, `spec`, `tests`, and `supply-chain`; it runs after landing. Landing applies no merge queue. Caller chain: the pre-commit hook `gate-set` runs `run_gate` (pipelines_hooks/cli.py:101) and then `main` in `pipelines_hooks/gate_runner.py:124`, which calls `run_set` (pipelines_hooks/gate_runner.py:74) with `published_sets` (pipelines_hooks/gate_sets.py:93). Shape: the partition lives in `pipelines_hooks/gate_sets.toml`, loaded by `load_gate_sets` (pipelines_hooks/gate_sets.py:56) into the frozen `GateSets` (pipelines_hooks/gate_sets.py:35); the loader already refuses a missing or ninth blocking gate, so the declaration is the one helper to reuse. | The partition test asserts both sets' exact membership from the published gate configuration and asserts that the full set is the fast set's complement within the eight blocking gates. Tests: `tests/hooks/test_gate_sets.py::test_the_fast_set_is_exactly_the_five_pre_land_gates`, `tests/hooks/test_gate_sets.py::test_the_full_set_is_exactly_the_complement_within_the_eight`. |
| `PIPE-GATES-R002` | **Auto-revert versus fix-forward.** A failed post-land gate triggers a recorded decision. The failure class decides it. The gate runner classifies each failure as `product` or `infrastructure`. An infrastructure failure means the gate produced no result, for example a lost runner. An unclassified failure is `product`. Auto-revert is the default; it reverts the failed changeset without operator action. Fix-forward applies only when the owner opens a fix-forward task within 300 s of the failed verdict. A passing re-run never changes the decision for a product failure. An infrastructure failure may re-run once. A passing re-run records `infrastructure-rerun`, and nothing reverts. The decision record carries the gate ID, the changeset ID, the verdict, the failure class, the threshold that fired, and the evidence digest. The record is replayable. Caller chain: the engine-side post-land step of the migration waves (`PIPE-GATES-R006.1`) will call `decide` (pipelines_hooks/landing_policy.py:116) after a failed full-set verdict; no production caller exists yet, only `tests/hooks/test_landing_policy.py`. Shape: the policy is the pure function `decide` (pipelines_hooks/landing_policy.py:116) over the frozen records `FailedVerdict` (pipelines_hooks/landing_policy.py:53), `FixForwardTask` (pipelines_hooks/landing_policy.py:66) and `SecondRun` (pipelines_hooks/landing_policy.py:73); it returns `DecisionRecord` (pipelines_hooks/landing_policy.py:84), which `replay` (pipelines_hooks/landing_policy.py:162) and `to_dict` (pipelines_hooks/landing_policy.py:204) serialize; the next change adds the caller in the landing step and reuses `replay` for the audit record. | The policy test asserts the decision and the complete record for each failure class and threshold. A product failure whose re-run passes auto-reverts. Tests: `tests/hooks/test_landing_policy.py::test_no_task_and_a_failing_second_run_auto_reverts`, `tests/hooks/test_landing_policy.py::test_a_task_inside_the_window_is_fix_forward`, `tests/hooks/test_landing_policy.py::test_an_infrastructure_failure_whose_rerun_passes_is_an_infrastructure_rerun`. |
